# m03.04 — MCP, scripted client & companion skill

_Parent: [`m03-api-mcp.md`](m03-api-mcp.md)_

_Status: **Draft — pending operator approval.**_

Two lanes, split by where the source lives. Text that arrives in a chat window — a pasted chores list, an uploaded short plan, a task named in conversation — goes through the MCP: conversational task work, plus landing a pasted list as one batch. Anything on disk goes through a script run by a coding agent: the agent has a shell, so a deterministic client does the mechanics and the agent keeps the judgment. Arc 4's first pass ([archived record](archive/m03.04-companion-skill+mcp-refinement.md)) built an import ceremony that policed the second case through the first lane; it retires here, and the drive findings it encoded become the importer's requirements.

## Requirements

Operator-stated, 2026-09-04. Every worklist below serves these; none is optional or "first".

1. Imports work smoothly through the skill, the API, and scripts — none of the failures the first pass and m03.03 fought: dropped or flattened items, open-only imports, title-echo descriptions, invented layers, chunk games, replayed batches.
2. Any chatbot with the MCP — a hosted one included — takes a dropped-in `PLAN.md` or `Chores.txt`, or a list the user typed by hand, and lands a faithful tree without being asked: completed items arrive done, source order kept, source grain kept (every level mapped, none invented), item prose carried as a description where it adds detail, numbering matched to the source, provenance as one root comment, nothing journaled into descriptions.
3. One-at-a-time task entry through the chat client.
4. Restructuring through the chat client — reorder, reparent, promote/demote, split into subtasks, merge, retitle — while the user edits the same tree in the web UI: the chatbot re-reads the pertinent live tree section before acting and never overwrites a newer human edit.
5. The chatbot completes tasks and checks them off, and speaks to the user by number and title and URL, never ids.
6. Prompt-injection defenses in the MCP, the skill, and the API, using best practices where they fit: tree content returned to an agent is delimited as data; instructions found in a source document or a task are represented, never followed, and flagged; per-Initiative agent access and member trust stay; irreversible operations stay out of the API.
7. Everything else the first pass bought that no server hook carries — swept from the archived record and either re-stated here by name or dropped by name.
8. This repo's plan imports into an Initiative and M04 runs from it, a coding agent working it through the CLI.
9. A coding agent keeps its own working todo list in an Initiative while it builds something, the user editing alongside in the web UI.
10. A newcomer gets going from the connect paste and an installable skill alone — no shell archaeology, no prior knowledge.

2. [ ] **Scripted client — one file, no dependencies, ships with the skill.**

	`skills/doitlist/scripts/doitlist.py` (name open): Python 3 standard library only. Reads `DOITLIST_API_URL` and `DOITLIST_API_TOKEN`, the variables the connect panel already emits. Runs on the agent's machine, not in the container. The agent acts on ids and speaks labels; the operator sees URLs and labels.

	1. [ ] **Read verbs.** `list` prints name and URL per Initiative. `tree <initiative> [--depth n]` prints an indented text outline — label, id, title, progress, done mark — never JSON. `comments <task>`. `activity <initiative>`.
	2. [ ] **Write verbs.** `add <parent> "title"`, `done <task>`, `progress <task> <n>`, `move <task> <new-parent> [position]`, `comment <task> "text"`, `retitle <task> "title"`, `describe <task> "text"`. Each is a one-op batch through the operations endpoint; `expected_version` threaded when the preceding read supplied one.
	3. [ ] **Import.** `import <file> [--into <initiative>] [--under <task>]` — one markdown checklist or plan file becomes a tree; a plan with sub-documents is the agent's composition, one import per file.
		1. [ ] Manifest first: the whole source parses before any write — stable source ids, parents, titles under the cap, done state, order.
		2. [ ] Source order preserved; nested checkboxes nest; `- [x]` and `N. [x]` both count; a checked item lands `done: true`.
		3. [ ] The file's top heading maps to the Initiative itself (or to the `--under` task): provenance is one comment naming the path, never a wrapper task.
		4. [ ] Prose under an item becomes its description only when it adds detail the title lacks; nothing invented, nothing journaled into descriptions.
		5. [ ] Numbering matches the source scheme: `1.`/`M1` → `numerical`; `I.A.2` → `outline`; `I`/`II` → `roman`; `A`/`B` → `alphabetical`; plain bullets → `none`.
		6. [ ] Chunks at the 150-op cap, one idempotency key per chunk, a parent and its subtree together by lid; a failed chunk reconciles against a tree read, never replays from memory.
		7. [ ] Prints the same shape summary as 1.3, plus the URL.
	4. [ ] **Diff.** `diff <file> <initiative>` — source items against the tree: missing, extra, done-state mismatches, order mismatches. Read-only; the agent decides what to do.
	5. [ ] **Windows.** Runs under PowerShell unchanged; the connect panel's per-shell pastes gain the script's env lines and a `python3 --version` check line.
	6. [ ] **Tests under `mix test`.** `python3` added to the Dockerfile; one ExUnit test runs the script's unittest suite — parser → operations, chunking, keys, done mapping, order, diff — and asserts a clean exit, so `mix test` stays the only gate.
