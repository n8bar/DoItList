# m03.05 — Documentation & maintenance

_Parent: [`m03-api-mcp.md`](m03-api-mcp.md)_

_Status: **Scoped — pending operator approval.** No implementation until approved._

One file. `docs/specs/agent_integration.md` grows to cover the HTTP API, the MCP server, and the scripted client alongside the promises it already states. Written for the operator and their agents, not published to the web. Motivated by a stale example that cost a debugging session (`progress` vs `manual_progress`): the contract is only as trustworthy as the docs describing it, and docs nobody maintains rot silently.

**Plain English, few words — tables included.** Prose stays under 600 words; today's spec is 434, so spend the rest on what a reader cannot infer from a table. A table gets one row per thing and the fewest columns that answer a real question — no column restating another, no sentences inside cells. A table's length comes from how many things exist, never from how they are described.

**The approach.** Anything mechanical is generated from the code and gated by a test, so it cannot go stale. Anything that needs a human voice — setup, walkthroughs, the why — is hand-written, and only that part relies on care. The generator and the drift guard are one mechanism: the generated text is committed, and a test regenerates it and compares. A stale doc fails the suite.

This arc runs last and then continuously. Public documentation waits for the milestone that exposes the API publicly.

1. [ ] **Shape the one file.**

	Settle the layout before writing, so the generator has somewhere to write to.

	1. [ ] Add a surface section to `agent_integration.md` for the API, the MCP, and the script.
	2. [ ] Fence every generated block with begin and end markers that name its source module.
	3. [ ] Say at the top which parts are generated and that hand-edits inside the fences are lost.
	4. [ ] Keep each promise stated once, where it belongs, and cite it from the surface sections rather than repeating it.

2. [ ] **The generator and its gate.**

	One mix task writes every generated block. One test proves the committed text still matches the code.

	1. [ ] **Write `mix doit.docs.gen`.** It rewrites the fenced blocks in place and leaves prose untouched.
		1. [ ] Read the op table from `DoItWeb.Api.Operations` — every wired verb and type, its accepted data keys, and its errors.
		2. [ ] Read response shapes from `DoItWeb.Api.Serializer`.
		3. [ ] Read the MCP tool list from the running adapter's `tools/list`.
		4. [ ] Read the scripted client's verbs and options from `doitlist.py --help`.
		5. [ ] Refuse to write if a fence is missing or unbalanced, naming the file.
	2. [ ] **Gate it with a test.** Regenerate into memory, compare against the committed files, and fail with the diff when they differ.
	3. [ ] Add the task to `mix precommit`, so a contract change that skips the docs cannot land.

3. [ ] **API section.**

	1. [ ] **Write the auth section.** The `doit_pat_` bearer scheme, where tokens come from, and how they are revoked.
	2. [ ] **Write the error section.** What `401`, `403`, `404`, and `429` each mean here, and what a client should do about each.
		1. [ ] Say plainly that an Initiative with agent access off reads as not found, not forbidden.
	3. [ ] **Write the operations envelope section.** How a batch is shaped, how `lid` forward references work, and what is atomic.
	4. [ ] Drop in the generated op table and the generated response shapes.
	5. [ ] **Write the read and write field split.** Name `progress` as read-only and `manual_progress` as the writable one, the confusion that motivated this arc.

4. [ ] **MCP section.**

	2. [ ] **Write how each tool maps onto the HTTP API**, so a reader can fall back to the API when a tool is missing.

5. [ ] **Scripted client section.**
