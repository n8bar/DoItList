# m04.04 — Concurrent-User Efficiency
_Parent: [`m04-resilient-client.md`](m04-resilient-client.md)_
_Status: Approved 2026-09-15_

## Goal

Increase the number of people one bounded deployment can serve by removing work that multiplies unnecessarily with viewers, rooms, or reconnects by multiple orders of magnitude.

## Worklists

1. [ ] **One persistence and publication path** — fan-out stays recipient-linear and payloads stay proportional to changed records/lineage, never recipient count multiplied by tree size.
   1. [ ] Profile an ordinary task write from request through transaction, serialization, PubSub, channel delivery, and client application.
   2. [ ] Consolidate validation, persistence, canonical serialization, and derived computation into one per-committed-operation path.
   3. [ ] Eliminate subscriber-side database reloads and tree rendering from durable delta fan-out.

2. [ ] **Snapshots, idle clients, and slow clients**
   1. [ ] Cache or share unchanged versioned snapshots where measurement shows simultaneous readers otherwise rebuild identical trees.
   2. [ ] Prove idle connections perform no polling, periodic tree reads, or rerenders.
   3. [ ] Handle lagging clients without delaying healthy clients.
      1. [ ] Bound channel mailboxes and delivery buffers.
      2. [ ] Make a lagging client discard its backlog and resnapshot.
   4. [ ] Bound transient collaboration work.
      1. [ ] Bound presence and chat fan-out state.
      2. [ ] Prevent reconnects from duplicating membership or presence work.

3. [ ] **Operational visibility**
   1. [ ] Add low-cardinality telemetry following [Phoenix Telemetry](https://hexdocs.pm/phoenix/telemetry.html).
      1. [ ] Measure operation latency and transaction time.
      2. [ ] Measure delta size and fan-out count/time.
      3. [ ] Measure snapshot build/cache behavior.
      4. [ ] Measure channel lag/resync, queue depth, reconnects, and failures.
   2. [ ] Expose development/test resource summaries.
      1. [ ] Connect latency changes to CPU, memory, and network volume.
      2. [ ] Connect latency changes to database connections, queries, and locks; support query findings with [PostgreSQL `EXPLAIN`](https://www.postgresql.org/docs/current/using-explain.html).
   3. [ ] Document healthy ranges, saturation signals, and the first diagnostic step for each signal in plain language.

4. [ ] **Capacity profiles and measured optimization**
   1. [ ] Build a containerized load driver with deterministic capacity profiles.
      1. [ ] Profile one Initiative with 1,000 watchers.
      2. [ ] Profile 10,000 connected users across thousands of Initiatives with 1,000 active editors.
      3. [ ] Profile idle soak and write bursts.
      4. [ ] Profile reconnect storms.
   2. [ ] Make every profile run reproducible.
      1. [ ] Record the capped environment.
      2. [ ] Record warm-up, duration, sample count, and percentiles.
      3. [ ] Fix the machine-readable report format.
   3. [ ] Exercise escalating load with thresholds declared first ([k6 load-testing guide](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/); [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)).
      1. [ ] Run smoke and average-load profiles.
      2. [ ] Run stress and spike profiles.
      3. [ ] Run soak profiles.
   4. [ ] Measure the current implementation and ratify numeric budgets with the operator before optimization.
   5. [ ] Optimize measured bottlenecks in descending impact; record before/after evidence and stop when all budgets pass.
   6. [ ] Verify the scaling curve at multiple client and write levels so one lucky maximum-load run cannot hide nonlinear collapse.
   7. [ ] Publish the measured capacity result without claiming extrapolated unlimited scale.
      1. [ ] State the supported capacity envelope and its assumptions.
      2. [ ] State the limiting resource and safe operating margin.

5. [ ] **Testing**
   1. [ ] [Agent] Test publication and fan-out deterministically.
      1. [ ] [Agent] Verify one commit emits one delta and rollback emits none.
      2. [ ] [Agent] Verify validation, persistence, canonical serialization, and derived computation run once per committed operation.
      3. [ ] [Agent] Verify fan-out performs no per-recipient database read.
      4. [ ] [Agent] Verify fan-out scales with recipients and payload scales with changed records/lineage, not recipient count multiplied by tree size.
      5. [ ] [Agent] Verify duplicate delivery is harmless.
      6. [ ] [Agent] Verify lag forces bounded resync.
   2. [ ] [Agent] Run every capacity profile repeatedly in clean, capped containers and verify machine-readable reports against the fixed budgets.
   3. [ ] [Agent] Confirm reconnect and overloaded-server behavior still acknowledges every user action under `UX_GUARDRAILS.md` §6.
   4. [ ] [Guided] Review one passing and one deliberately failing report with the operator; identify the bottleneck from evidence before revealing the injected cause.

## Exit

The reference deployment has a documented, repeatable capacity envelope and no known viewer-amplified database or rendering path.
