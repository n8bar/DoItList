# m04.04 — Concurrent-User Efficiency
_Parent: [`m04-resilient-client.md`](m04-resilient-client.md)_
_Status: Goal approved 2026-09-15 · Worklists unapproved_

## Goal

Increase the number of people one bounded deployment can serve by removing work that multiplies unnecessarily with viewers, rooms, or reconnects by multiple orders of magnitude.

## Worklists

1. [ ] **One persistence and publication path**
   1. [ ] Profile an ordinary task write from request through transaction, serialization, PubSub, channel delivery, and client application.
   2. [ ] Ensure validation, persistence, canonical serialization, and derived computation happen once per committed operation, not per connected viewer.
   3. [ ] Eliminate subscriber-side database reloads and tree rendering from durable delta fan-out.
   4. [ ] Keep fan-out proportional to recipients and payload proportional to changed records/lineage, never recipient count multiplied by tree size.

2. [ ] **Snapshots, idle clients, and slow clients**
   1. [ ] Cache or share unchanged versioned snapshots where measurement shows simultaneous readers otherwise rebuild identical trees.
   2. [ ] Prove idle connections perform no polling, periodic tree reads, or rerenders.
   3. [ ] Bound channel mailboxes and delivery buffers; make a lagging client discard backlog and resnapshot without delaying healthy clients.
   4. [ ] Bound presence and chat fan-out state and prevent reconnects from producing duplicate membership/presence work.

3. [ ] **Operational visibility**
   1. [ ] Add low-cardinality telemetry for operation latency, transaction time, delta size, fan-out count/time, snapshot build/cache, channel lag/resync, queue depth, reconnects, and failures, following [Phoenix Telemetry](https://hexdocs.pm/phoenix/telemetry.html).
   2. [ ] Expose development/test summaries that connect latency changes to CPU, memory, database connections/queries/locks, and network volume; support query findings with [PostgreSQL `EXPLAIN`](https://www.postgresql.org/docs/current/using-explain.html).
   3. [ ] Document healthy ranges, saturation signals, and the first diagnostic step for each signal in plain language.

4. [ ] **Capacity profiles and measured optimization**
   1. [ ] Add deterministic profiles for one Initiative with 1,000 watchers; 10,000 connected users across thousands of Initiatives with 1,000 active editors; idle soak; bursts; and reconnect storms, plus a containerized load driver.
   2. [ ] Record the capped environment, warm-up, duration, sample count, percentiles, and report format.
   3. [ ] Progress from smoke through average, stress, spike, and soak loads, declaring pass/fail thresholds first ([k6 load-testing guide](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/); [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)).
   4. [ ] Measure the current implementation and ratify numeric budgets with the operator before optimization.
   5. [ ] Optimize measured bottlenecks in descending impact; record before/after evidence and stop when all budgets pass.
   6. [ ] Verify the scaling curve at multiple client and write levels so one lucky maximum-load run cannot hide nonlinear collapse.
   7. [ ] Publish the supported capacity envelope, assumptions, limiting resource, and safe operating margin without claiming extrapolated unlimited scale.

5. [ ] **Testing**
   1. [ ] [Agent] Run deterministic tests that one commit emits one delta, rollback emits none, fan-out performs no per-recipient database read, duplicates are harmless, and lag forces bounded resync.
   2. [ ] [Agent] Run every capacity profile repeatedly in clean, capped containers and verify machine-readable reports against the fixed budgets.
   3. [ ] [Agent] Confirm reconnect and overloaded-server behavior still acknowledges every user action under `UX_GUARDRAILS.md` §6.
   4. [ ] [Guided] Review one passing and one deliberately failing report with the operator; identify the bottleneck from evidence before revealing the injected cause.

## Exit

The reference deployment has a documented, repeatable capacity envelope and no known viewer-amplified database or rendering path.
