# m04.07 — Product Cutover & Hardening
_Parent: [`m04-resilient-client.md`](m04-resilient-client.md)_
_Status: Goal approved 2026-09-15 · Worklists unapproved_

## Goal

Finish the product-wide client-rendering mandate, remove the old path, and prove the complete product under real interaction, concurrency, and failure conditions.

## Worklists

1. [ ] **Remaining product surfaces**
   1. [ ] Migrate the Initiatives index and personal workspace, including sorting, dragging, archive/hidden views, Assigned to Me, collaborators, notifications, and live list changes.
   2. [ ] Migrate account/preferences, authentication/session screens, member management, Initiative settings, import approval, comments, activity, chat, and shared chrome.
   3. [ ] Preserve all permissions, confirmations, optimistic/in-flight feedback, deep links, presence continuity, and live updates from the inventory.
   4. [ ] Keep low-frequency surfaces simple while using the same runtime, form/error primitives, session boundary, and domain paths.

2. [ ] **Legacy removal**
   1. [ ] Route all product paths through the client bootstrap and remove interactive LiveView rendering, DOM-patch preservation, duplicate hooks, and obsolete assigns/events.
   2. [ ] Remove dead assets, compatibility state, and tests that only protect the retired implementation; retain domain and protocol coverage.
   3. [ ] Verify no route can accidentally fall back to a stale second interface and no client business rule bypasses server authorization/validation.
   4. [ ] Update architecture, development, troubleshooting, and deployment documentation for the final boundary.

3. [ ] **Failure and concurrency matrix**
   1. [ ] Automate slow request, dropped request, dropped acknowledgement, duplicate delta, out-of-order delta, sequence gap, disconnect, reload, tab crash, server restart, deploy, crash loop, reconnect storm, and slow-client cases.
   2. [ ] Cover simultaneous field edits, edit/delete, completion/move, permission change, membership removal, Initiative switch, and logout with pending work.
   3. [ ] Prove each case has immediate acknowledgement, bounded resource use, no duplicate accepted work, no silent pending-work loss, correct authorization, and eventual convergence or a clear terminal outcome.
   4. [ ] Run the matrix over WebSocket and LongPoll where the transport can change behavior.

4. [ ] **Whole-product quality gate**
   1. [ ] [Agent] Run unit, property, integration, browser, accessibility, security, performance, load, soak, and failure suites from clean containers.
   2. [ ] [Agent] Re-run all approved capacity and large-Initiative profiles against fixed budgets and publish the final comparison and supported envelope.
   3. [ ] [Agent] Audit every inventoried action against `UX_GUARDRAILS.md` §6 and §7; no interaction waits silently or loses its state on navigation/reconnect.
   4. [ ] [Agent] Confirm every endpoint, operation, field, and tool is represented in [`agent_surfaces.md`](../../reference/agent_surfaces.md) and the generated gate is clean.
   5. [ ] [Agent] Run `docker compose run --rm web mix precommit` and production asset/container builds.

5. [ ] **Guided product pass**
   1. [ ] [Guided] Use two accounts and multiple windows to create, edit, restructure, filter, comment, manage members, navigate, disconnect, reload, and recover while observing pending and remote state.
   2. [ ] [Guided] Read the load/capacity report together and identify the supported envelope, safety margin, limiting resource, and signals that future growth is approaching it.
   3. [ ] [Human] Complete the desktop/narrow, keyboard/touch, light/dark, reduced-motion, button-recognition, error-copy, and recovery-confidence pass.

6. [ ] **Close-out**
   1. [ ] Resolve or explicitly rehome every omission found during the full pass; none remain as an unowned note in a closed arc.
   2. [ ] Update milestone status, PLAN, completion date, and CHANGELOG only after all acceptance criteria and guided checks pass.
   3. [ ] Record the next measured capacity trigger and the exact command future work uses to detect it.

## Exit

One client-rendered product remains, its failure and capacity boundaries are known, and M05 can add features without rebuilding them across two frontend architectures.
